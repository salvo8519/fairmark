## Problem
Analysts build a model from a start date, a frequency and a number of periods; the model then
needs the period dates, the length of each period and a row of values grown from a base. An
AI agent asked to do this today must compute the dates itself (month ends, February, leap
years) and the projected values itself, before passing them to `tvm.xnpv` or `tvm.xirr`. These
are the computations where errors are silent: 31 January plus one month, a schedule that
drifts from the 31st to the 28th, a period end read as inclusive in one place and exclusive in
another, an annual growth applied unchanged to monthly periods, a first value that is or is
not already grown. `dates.schedule` builds the periods as financial markets define them, and
`series.project` builds the values on the same periods, with outputs that feed `tvm.xnpv`,
`tvm.xirr` and, later, the DCF with dated periods (#167).

## Scope
**In scope:**
- `dates.schedule`: from a start date, a period length and a number of periods, the start date
  and end date of every accrual period [start, end) and, under a stated day count, its year
  fraction. The period length is given either as a named frequency or as a whole number of
  months (`period_months`).
- `series.project`: from a base value, a growth rule (constant, linear between two rates, one
  rate per period) and a timeline (a number of periods with an optional period length, or a
  schedule defined as for `dates.schedule`), the projected value of every period; conversion of
  an annual growth rate to the period length with an explicit convention.
- Frequencies of 12, 6, 4, 3, 2 and 1 periods a year, defined once in the core and shared by
  the compounding list (`rates.convert`, `tvm.xnpv`, `tvm.xirr`, `loans.*`) and the loan payment
  frequency (`loans.*`).

**Out of scope (future extensions, designed to be additive):**
- Business-day calendars and business-day conventions: every date of version 1 is unadjusted.
- A termination date instead of a number of periods; stub periods; backward generation.
- Period lengths that are not whole months (days, weeks).
- A period length in months for compounding or payment frequencies: those remain periods per
  year (R20).
- Payment dates distinct from period dates, mid-period dates, payment lags.
- Period labels and fiscal calendars (calendar or fiscal year, half, quarter, month of each
  period): to be reconsidered only if users ask for them (Decision E).
- Rounding of projected values; growth rules other than the three above.
- Any change to `dcf.*`: the DCF with dated periods is specified by #167.

## User stories
- As an analyst, I want the quarterly periods of the next five years from 31 December 2025,
  so that my dated flows fall on 31 March, 30 June, 30 September and 31 December without typing
  them.
- As an analyst, I want a monthly schedule that starts on 31 January to keep month ends (29
  February, then 31 March) and never drift to the 29th, so that the dates match my ledger.
- As an analyst, I want to say "every 18 months" or "every 24 months" as a number of months,
  so that a tenor without a common name needs no workaround.
- As an analyst, I want revenues of 1,000 grown at 12% a year, projected monthly, with the
  annual-to-monthly conversion stated, so that I know whether twelve months compound to 12%.
- As an AI agent, I want one unambiguous meaning of a period's end date, stated in the method
  description and the schema, so that I never count the end date twice.
- As an AI agent, I want `series.project` to return dated values in the shape of the
  `cash_flows` of `tvm.xnpv`, so that I never retype a date or a number.

## Requirements (EARS)

### dates.schedule
- **R1** — WHEN given a start date, a period length and a number of periods n, THE ENGINE SHALL
  return n contiguous accrual periods. Period k runs from and including its start date to but
  excluding its end date, [start_k, end_k), as the calculation periods of the 2006 ISDA
  Definitions; start_1 is the start date; end_k = d_k (R2); start_{k+1} = end_k. The end date of
  a period is therefore the first day of the next period and is not part of the period; there
  is no inclusive "last day" field. THE ENGINE SHALL state this definition in the method
  description, in the schema description of the start and end date fields and in
  `explain.conventions`.
- **R2** — THE ENGINE SHALL generate every date from the start date, not from the previous
  date: d_k = start date + k × p months, with p the months per period (R3), so that a day
  shortened in one period (31 January to 29 February) is restored in the next (31 March) and
  the schedule never drifts. The day of month SHALL follow the end-of-month rule, which is
  fixed: WHEN the start date is the last day of its month, every date is the last day of its
  month (30 June quarterly: 30 September, 31 December, 31 March, 30 June); otherwise every date
  keeps the day of the start date, or the last day of the month when that month is shorter (30
  January monthly: 28 February, 30 March). This is the end-of-month convention of ISDA and ICMA
  practice; THE ENGINE SHALL report in `explain.conventions` whether the start date is a month
  end and whether the rule changed any date.
- **R3** — THE ENGINE SHALL accept the period length in exactly one of two forms:
  - `frequency`, a named frequency: `monthly` (12 periods a year, 1 month per period),
    `bimonthly` (6, 2 months), `quarterly` (4, 3 months), `four_monthly` (3, 4 months),
    `semi_annual` (2, 6 months) or `annual` (1, 12 months); each name maps to its tenor in
    months, as the QuantLib `Frequency` values map to `Period` tenors;
  - `period_months`, the tenor as a positive whole number of months (1, 2, 3, 4, 6, 12, and any
    other positive integer such as 5, 18 or 24), as QuantLib `Period(n, Months)` and
    python-dateutil `relativedelta(months=n)`. The name states months per period, so that it
    cannot be confused with a compounding frequency, which is a number of periods per year.
  A named frequency and the equal number of months produce identical results (`quarterly` and
  `period_months` 3). IF both forms or neither are given, THEN THE ENGINE SHALL return
  `FM-E001` naming `/frequency` and `/period_months` and stating the fix (give exactly one). IF
  `period_months` is 0 or negative, THEN it SHALL return `FM-E001` naming `/period_months`. THE
  ENGINE SHALL state the mapping of names to tenors in the method description and in the
  schema descriptions of both fields, and SHALL report in `explain.conventions` the months per
  period and which form gave it.
- **R4** — WHEN a day count (the five day counts of SPEC-0002 R2) is given, THE ENGINE SHALL
  return the year fraction of every period from its start date to its end date, computed by the
  day-count function of `dates.year_fraction` on [start, end) (no second implementation). WHEN
  no day count is given, THE ENGINE SHALL return no year fraction and SHALL state in
  `explain.conventions` that none was computed (Decision 1).
- **R5** — THE ENGINE SHALL produce unadjusted dates and SHALL report it in
  `explain.conventions`; fields for an end date, a calendar, a business-day convention or a
  stub are not part of version 1 and SHALL be refused as unknown fields (`FM-E001`).
- **R6** — THE ENGINE SHALL return `start_dates` and `end_dates` (one per period, in order),
  `year_fractions` (with a day count, one per period), `months_per_period` and, WHEN the months
  per period divide 12, `periods_per_year` (12 / p, a whole number).
- **R7** — IF the number of periods is 0 or above 10000, THEN THE ENGINE SHALL return `FM-E001`
  naming `/number_of_periods`; IF the start date is malformed, impossible or out of range, THEN
  it SHALL return `FM-E009` naming `/start_date`; IF a generated date falls after 2199-12-31,
  THEN it SHALL return `FM-E009` naming `/number_of_periods`, the last valid period and the
  first date out of range, with the fix (fewer periods or a shorter period length). Month
  arithmetic SHALL use a range that cannot overflow for any accepted input.
- **R8** — THE ENGINE SHALL include in `explain`: the period definition [start, end); the
  generation rule stated once with its formula; the period length with its months per period,
  the form that gave it and, when defined, its periods per year; the end-of-month rule and its
  effect; the day count, or the statement that none was given; and, with a day count, the year
  fraction of the first period with the numbers substituted (the formula of
  `dates.year_fraction`) and the sum of the year fractions. The output vectors carry the
  per-period numbers, as the rows of `loans.amortisation_schedule` (SPEC-0009 Decision 8); the
  number of steps is bounded and independent of n.

### series.project
- **R9** — WHEN given a base value V_0, a growth rule, a base period and a timeline of n
  periods, THE ENGINE SHALL return the projected value of every period 1..n by the recurrence
  V_k = V_{k−1} × (1 + g_k), computed period by period (never by a closed-form power), where
  g_k is the growth rate per period into period k after any conversion (R13).
- **R10** — THE ENGINE SHALL require the base period, with no default (Decision 3):
  - `period_0`: the base value is the value before the first period (for example the last
    actual year); V_1 = V_0 × (1 + g_1); n growth steps;
  - `period_1`: the base value is the value of period 1; V_1 = V_0; growth steps into periods
    2..n only (n − 1 steps).
  The returned values are always those of periods 1..n.
- **R11** — WHEN the growth rule is `constant` with rate g, THE ENGINE SHALL apply g to every
  growth step. WHEN it is `linear` from `from_growth` to `to_growth` over s growth steps, THE
  ENGINE SHALL apply g_j = from_growth + (to_growth − from_growth) × j / s for j = 1..s, so that
  `to_growth` is reached in the last step and `from_growth` is the growth before the first step
  (SPEC-0001 Decision 4; Decision 4 below); the rule applies to rising and falling growth.
- **R12** — WHEN the growth rule is `per_period`, THE ENGINE SHALL apply the listed rates in
  order, one per growth step; IF the list does not have exactly s elements, THEN it SHALL return
  `FM-E001` naming `/growth/per_period/growth_rates` with the expected and the actual count and
  the base period that sets the count.
- **R13** — THE ENGINE SHALL interpret the rates of the rule by the growth basis. With p the
  months per period of the timeline:
  - `per_period`: the growth per period of the timeline, used as given, for any p;
  - `annual_compound`: an annual growth g, converted to the growth per period that compounds
    exactly to g over a year. WHEN p divides 12 (m = 12 / p periods a year), the rate per period
    is (1 + g)^(1/m) − 1, computed through the conversion of `rates.convert` (equivalent rate
    with compounding m, divided by m). WHEN p is a multiple of 12 (k = p / 12 years per period),
    the rate per period is (1 + g)^k − 1, an exact integer power;
  - `annual_simple`: an annual growth g, converted in proportion to the period length: g / m
    when p divides 12, so that m periods compound to (1 + g/m)^m − 1, which differs from g; g × k
    when p is a multiple of 12.
  For `linear`, interpolation is made on the rates as given, then each rate is converted. The
  basis is required WHEN the timeline has a period length other than 12 months; it may be
  omitted WHEN the period length is 12 months (`annual` or `period_months` 12: the three bases
  coincide) or WHEN the timeline has no period length (the rates are per period by definition).
  An annual basis SHALL return `FM-E001` naming `/growth_basis` WHEN the timeline has no period
  length, or WHEN p neither divides 12 nor is a multiple of 12 (for example 5 or 18 months),
  with the fix (use `per_period` with rates per period, or a period length that divides 12 or
  is a multiple of 12). The case that applied SHALL be stated in `explain.conventions`, with the
  effective annual growth implied by each rate per period WHEN p divides 12.
- **R14** — THE ENGINE SHALL accept exactly one timeline form:
  - `periods`: a number of periods (1 to 10000) and an optional period length, given as at most
    one of `frequency` or `period_months` (R3; both return `FM-E001` as in R3); no dates;
  - `schedule`: a schedule definition, the same object as the input of `dates.schedule`; the
    periods are built by the `dates.schedule` function (typed call, ADR 0009), so the dates
    are identical by construction and nothing is copied or re-validated (Decision 6).
- **R15** — WHEN the timeline is `schedule`, THE ENGINE SHALL require a value timing,
  `end_of_period` (the value is dated at the period end date, which is the first day of the next
  period, R1) or `beginning_of_period` (dated at the period start date), and SHALL return
  `dated_values`: one `{date, amount}` per period, the element shape of `cash_flows` in
  `tvm.xnpv` and `tvm.xirr`. WHEN the timeline is `periods`, a timing SHALL be refused with
  `FM-E001`. The methodology page SHALL show that end-of-period values of a schedule starting on
  1 January are dated 1 April, 1 July, and so on, and that a schedule starting on 31 December
  dates them on 31 March, 30 June, 30 September and 31 December.
- **R16** — THE ENGINE SHALL return one row per period with `period`, the rate as stated in the
  rule (before conversion), the rate per period applied (absent for period 1 under `period_1`),
  its implied effective annual growth WHEN the months per period divide 12, and `value`; with a
  `schedule` timeline every row also carries `start_date`, `end_date` and, with a day count,
  `year_fraction` of the period. It SHALL also return `values`, the values of periods 1..n as a
  flat list (the shape of `cash_flows` in `tvm.present_value`).
- **R17** — IF a growth rate as given, or a rate per period after conversion, is −1 or lower,
  THEN THE ENGINE SHALL return `FM-E001` naming the rate by its JSON pointer (the rule of
  SPEC-0001 R11); IF a value overflows the decimal range, THEN it SHALL return `FM-E008`.
- **R18** — WHEN the base value is negative, THE ENGINE SHALL report in `explain.conventions` as
  a warning that a positive growth makes the values more negative, and SHALL NOT refuse it
  (SPEC-0001 R11).
- **R19** — THE ENGINE SHALL include in `explain`: the recurrence stated once with its formula;
  the base value and base period; the growth rule with its parameters; the conversion of the
  first rate with the numbers substituted (when a conversion applies); the first projected value
  with the numbers substituted; the last value; and, with a `schedule` timeline, the schedule
  conventions of R8. The number of steps is bounded and independent of n.

### Shared frequencies (compounding and payment frequency)
- **R20** — THE ENGINE SHALL define the named frequencies of R3 (periods per year and months per
  period) in one place of the core; the compounding list (`Compounding`, used by
  `rates.convert`, `tvm.xnpv`, `tvm.xirr` and `loans.*`) and the loan payment frequency
  (`PaymentFrequency`, used by `loans.*`) SHALL take their periodic values from it. Both SHALL
  gain `bimonthly` (6 a year) and `four_monthly` (3 a year). `period_months` is not added to
  them.
- **R21** — WHEN a method that accepts a compounding or a payment frequency is called with
  `bimonthly` or `four_monthly`, THE ENGINE SHALL apply the formulas of the existing periodic
  values with m = 6 or m = 3 (growth (1 + r/m)^(m t), `FM-E003` when r/m ≤ −1, loan periodic
  rate per SPEC-0009 R1) and label it in `explain.conventions`. Results for every existing value
  SHALL be unchanged, bit for bit.
- **R22** — The extension of R20 is an additive input change (new enumeration values; no input
  changes meaning; no result changes): per ADR 0009 §4 it SHALL NOT create new method versions;
  the current schema files of the affected methods SHALL be regenerated with the added values
  only, and ADR 0008 §4 SHALL carry an amendment note (Decision 5).

### Common
- **R23** — No documented default is introduced by this spec: every choice is either required,
  fixed and reported (end-of-month rule, unadjusted dates, period definition), or optional with
  a stated effect of its absence (day count, growth basis under R13, period length of a
  `periods` timeline). WHEN a later version adds a default, it SHALL be reported in
  `explain.conventions` and in `meta.defaults_applied` (#197). This spec does not depend on #197
  (Decision 8).
- **R24** — Every error SHALL name the offending field by its JSON pointer and state the fix
  (ADR 0013). No new error code is introduced (Decision 7).

## Decisions (maintainer, 2026-11-08)
- [x] **A. Market practice.** Financial-market practice (ISDA) is followed, not spreadsheet
      conventions.
- [x] **B. Accrual periods.** Periods are [start, end); the end date is the start of the next
      period; no inclusive last-day field; year fractions on [start, end) (R1, R4).
- [x] **C. End-of-month rule.** Anchored to the start date, with the ISDA and ICMA end-of-month
      convention, applied as one fixed, reported rule with no input field; a `same_day` option
      can be added later as an additive value if a user needs it (R2).
- [x] **D. Simplification.** No payment timing or payment dates in `dates.schedule` (they equal
      the start or end dates); no year fraction from the start (given by
      `dates.year_fraction`); `series.project` takes the schedule definition instead of the
      dates returned by `dates.schedule`, so no copying or contiguity check is needed (R14).
- [x] **E. No period labels or fiscal calendars.** The period table with calendar labels
      (year, half, quarter, month), fiscal labels, `label_note` and `fiscal_year_start_month`
      proposed in revision 2 is removed, for stability and maintainability: which quarter or
      four-month period a range belongs to depends on the user, fiscal calendars differ, and
      the extra parameters would complicate the method. Listed under future extensions, to be
      reconsidered only if users ask.
- [x] **F. Period length in months.** The period length is given either as a named
      `frequency` or as `period_months`, the tenor in whole months, following QuantLib
      (`Schedule` built from `Period(n, Months)`; `Frequency` as named periods-per-year values)
      and python-dateutil (`relativedelta(months=n)`). Exactly one of the two; both or neither
      is `FM-E001` with the fix. The field is named `period_months` so that it cannot be read
      as a compounding frequency (periods per year). Any positive integer is accepted for the
      schedule: the date generation of R2 is defined for every whole number of months, the
      date range of R7 bounds it in practice, and a cap such as 12 would refuse common tenors
      (18 and 24 months) for no numerical reason. In `series.project` the annual growth bases
      convert only when the period length divides 12 (m periods a year, the equivalent rate of
      `rates.convert`) or is a multiple of 12 (k years a period, an exact integer power); other
      lengths (5, 7, 18 months) would need a fractional power of a year (5/12, 3/2) whose
      practical convention is not settled, so they accept only the `per_period` basis (R13).

## Resolved questions (maintainer, 2026-11-08: every recommendation accepted)
- [x] **1. Day count absent.** Resolved (a): no year fraction without a day count, stated in
      the conventions; a default day count would produce numbers on an assumption the user did
      not state (ADR 0008 §6). Rejected: (b) documented default `act_365_fixed`.
- [x] **2. Names of the two new frequencies.** Resolved (a): `bimonthly` and `four_monthly`,
      with unambiguous schema descriptions. Rejected: (b) `every_two_months` and
      `every_four_months`.
- [x] **3. Base period.** Resolved (a): required, with no default; the readings differ by a
      full period of growth on every value. Rejected: (b) documented default `period_0`.
- [x] **4. Linear rule.** Resolved (a): step j / s, `from_growth` before the first step
      (SPEC-0001 Decision 4), so that a series equals a DCF `linear_decline` stage and s = 1 is
      defined. Rejected: (b) step (j − 1) / (s − 1).
- [x] **5. Versioning of the compounding extension.** Resolved (a): additive change of the
      current versions (ADR 0009 §4), with an amendment note to ADR 0008 §4; the two values are
      added in one shared place (R20). If the CI schema check classifies an enumeration
      extension as non-additive, the implementation stops and the maintainer decides.
      Rejected: (b) new versions of every affected method.
- [x] **6. Timeline of `series.project`.** Resolved: `series.project` takes the schedule
      definition (R14), so the dates are identical by construction.
- [x] **7. Error codes.** Resolved: count mismatches use `FM-E001` (not a widened `FM-E025`,
      which is specific to DCF stages); a generated date after 2199-12-31 uses `FM-E009`; no
      new code.
- [x] **8. Order with #197.** Resolved: no default is introduced (R23), so this spec is
      implemented independently of #197.
